# 문장 스타일 기준 (덱·이력서 공통)

`scripts/check_style.py`가 이 기준으로 경고한다. 경고만 하고 빌드는 막지 않는다. deck.json·resume.json을 고치거나 빌드하면 프로젝트 훅(`.claude/hooks/style_check.py`)이 자동으로 돌린다.

## 적용 범위

| 문장 필드 (끝맺음·용어·길이 검사) | 구 필드 (용어·길이만, 명사로 끝나도 됨) | 검사 안 함 |
|---|---|---|
| 이력서: `text.items`·`body`, `projects.bullets` | 덱: `fit.items.desc`(인재상 풀이), `requirements.rows.evidence`(표 칸) | 라벨·이름·기간·팀·역할 줄, `stack`·`skills`, `metrics`, `keywords`, `tags`, `architecture.layers.items`, `image.steps`, 표 `rows`(이력서), `cover`·`section`의 문구 |
| 덱: `title`(주장형), `summary`, `intro`, `lead`, `context`, `problem`, `action`, `result`, `evidence`, `desc`, `contributions`, `caption`, `sub`, `message`, `notes` | | |

## 1. 끝맺음 — 단어로 끝내지 않는다

- **이력서는 "~했다" 체**, **덱은 "~했습니다" 체**. 한 문서 안에서 섞지 않는다.
- 개조식(명사로 끝나는 "…분리", "…유지", "…해제 완료", "…9/9")은 쓰지 않는다. 동사를 붙여 문장으로 끝낸다.
- 수치로 끝나는 문장은 무엇이 어떻게 바뀌었는지 동사로 맺는다: `52.6분 → 30.4분(−42.2%)` → `52.6분에서 30.4분으로 42.2% 줄였다`.
- 덱 제목: 주장형 제목은 "~했습니다"로 끝낸다. 18자 이하·쉼표 없는 라벨형 제목(`기술 스택`, `그 밖의 프로젝트와 활동`)은 명사로 둔다.
- 문장 끝 뒤에 붙는 출처 괄호 `(약관 ETL)`·링크는 괜찮다. 앞 문장이 서술어로 끝나야 한다.
- "배운 점:" 문장도 같은 체로 끝낸다(덱 `…는 별개라는 것을 배웠습니다`, 이력서 `…별개다`).

## 2. 용어 — 하는 일과 결과를 쉬운 말로

- 읽는 사람은 서류 심사관(이력서)과 면접관(덱)이다. 공고에 나오는 기술 이름(Kubernetes, CI/CD, PostgreSQL 등)은 그대로 쓴다.
- 내부 개념·옵션 이름·코드 식별자는 우리말로 풀고, 꼭 필요하면 원어를 괄호로 한 번만 붙인다.

| 피할 말 | 이렇게 |
|---|---|
| groundedness 검사 | 원문에 근거가 있는지 검사 |
| fail-closed | 검사가 실패하면 저장하지 않게 |
| freeze | 기존 위반은 기록해 두고(freeze) 새 위반만 막았다 |
| smoke 테스트 | PR마다 문서 1건으로 도는 간이 테스트 |
| generic plan / custom plan | 범용 실행 계획 / 값별 실행 계획 |
| prepared statement | 미리 준비해 재사용하는 쿼리 |
| afterCommit | 커밋 뒤 |
| fan-in | 결과를 청구 단위로 모으는 |
| dry-run | DB에 쓰지 않고 미리 실행 |
| fallback | 대체 처리 |
| `force_custom_plan`, `pg_stat_activity` 등 식별자 | 하는 일로 풀기("그 트랜잭션에서만 값별 실행 계획을 강제") |

- 한 문장에 영문 용어는 3개까지. 도구 이름 나열은 `stack`·보유기술에 맡기고, 문장에는 무엇을 왜 했고 무엇이 달라졌는지 쓴다.
- 덱 `notes`(발표 대본)와 star 상세에는 원어를 남겨도 되지만, 처음 나올 때 풀이를 붙인다.

## 3. 나열·길이

- 가운뎃점(`·`) 나열은 3개까지. 넘으면 대표 2~3개만 남기거나 문장 두 개로 나눈다.
- 화살표는 전후 한 쌍(`A → B`)만. 단계 흐름(`0/9 → 6/9 → 9/9`)은 덱 상세에서만 쓰고 이력서에서는 전후만 쓴다.
- 괄호는 문장당 2개까지.
- 길이: 이력서 bullet·text 110자, 덱 action 70자, result 80자, contributions 70자, evidence 90자. 넘으면 나눈다.

## 4. 바꾸지 않는 것

- 사실·수치·기여 범위. 문장을 다듬다 수치를 반올림하거나 바꾸지 않는다. 고친 뒤 `check_facts.py`를 다시 돌린다.
- 팀 성과 표기(`팀 검색 평가 R@5 0.894`).
- 공고 원문 인용(`requirements.rows.req`)과 고유명사는 경고가 나와도 그대로 둔다.

## 5. 고쳐 쓴 예

| 전 | 후 |
|---|---|
| 이미지 검수를 **@Async**로 분리하고 커밋 이후(afterCommit)에만 시작해 응답 지연과 롤백 후 검수 실행을 방지 | 이미지 검수를 **비동기로 분리**하고 커밋이 끝난 뒤에만 시작하게 해, 응답 지연과 롤백된 글의 검수 실행을 막았다 |
| LLM 출력을 믿지 않는 파이프라인 — OCR에서 표·저신뢰 페이지만 VLM으로 보완하고 groundedness 검사를 통과해야 채택, 잔류 PII 검사는 fail-closed | LLM 출력을 믿지 않는 파이프라인 — 표와 OCR 신뢰도가 낮은 페이지만 VLM으로 보완하고, 원문에 근거가 있는 결과만 채택했다. 개인정보가 남으면 저장하지 않게 막았다 |
| (덱 action) 파이프라인을 7단계로 나눠 단계별 계측 | 파이프라인을 7단계로 나눠 단계마다 시간을 쟀습니다 |
| (덱 result) 실환경 E2E 저장 0/9 → 9/9 | 실제 인프라에서 문서 9건이 모두 저장됐습니다 (0/9 → 9/9) |
| (덱 제목) psql에선 10ms인 쿼리가 부하에선 DB CPU 99%, 원인은 실행 계획 | psql에선 10ms인 쿼리가 부하에서 DB CPU를 99%로 만든 원인은 실행 계획이었습니다 |
